# Tramway Custom Pages

See the [main README's custom page section](https://github.com/Purple-Magic/tramway#tramway-crud) for the basic
config shape and example. This file covers the mechanics behind it.

## Why no extra wiring is needed

The built-in CRUD pages (`index`/`show`/`create`/`update`/`destroy`) are all routed to Tramway's own
`Tramway::EntitiesController`, which is shared across every entity. A Custom Page is different: its route is
generated by Tramway, but it's dispatched to **your own** controller, resolved purely by Rails' normal naming
convention from the entity's `namespace`/`name` — the same controller Rails would infer for a plain
`resources :users` call nested in that namespace. Tramway never defines that controller for you; you add it
yourself under `app/controllers/...`.

Making that controller inherit from `Tramway::EntitiesController` (instead of your app's usual base controller) is
what makes the Custom Page "look like" the rest of the entity's pages for free:

- `layout 'tramway/layouts/application'` is inherited, so the page gets the same `<head>`/body shell and the
  `tramway_navbar` call the layout renders.
- `helper Tramway::ApplicationHelper` and the gem's `prepend_view_path` are inherited, so `tramway_*` view helpers
  and the gem's own partials are available in your Custom Page view exactly like in `index`/`show`.
- The private `entity`/`model_class` lookups are inherited, so `model_class.find(params[:id])` works the same way
  it does inside Tramway's own controller actions.

Your own view at the conventional path for that controller/action (e.g. `app/views/admin/users/impersonate.html.haml`
for `Admin::UsersController#impersonate`) is found by Rails' normal view lookup. Tramway's `prepend_view_path` only
*adds* a place to look first; it doesn't replace your app's own view paths, so Rails still falls through to your
view once it doesn't find a template of that name inside the gem.

## Route shape

- `member: true` nests the route under `/:id` (e.g. `/admin/users/:id/impersonate`), matching Rails'
  `resources do member do ... end end`. Omit it (default `false`) for an entity-level route with no id (e.g.
  `/admin/users/impersonate`).
- `via:` sets which HTTP method(s) the route matches (default `:get`). Pass an array (e.g. `via: %i[get post]`) to
  accept more than one on the same action.
- `params:` appends extra required path segments after the action name, in order (e.g. `params: [:redirect_to]`
  on a member page produces `/admin/users/:id/impersonate/:redirect_to`). They arrive in the controller as regular
  `params` entries, same as `:id`.

These three options only affect pages whose `action` is not one of the built-in CRUD actions; they're ignored on
`index`/`show`/`create`/`update`/`destroy` pages, whose route shape is fixed by Tramway's own REST conventions.

## Route helper names

Tramway doesn't assign an explicit route name for Custom Pages — it lets Rails derive one the same way it would for
any `member`/`collection` route added to a `resources` block. For the `impersonate` example above, that's
`impersonate_admin_user_path(user_id, redirect_to_value)`.
